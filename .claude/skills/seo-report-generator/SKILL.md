# SEO Report Generator

## Purpose

Convert confirmed SEO audit findings into a ready-to-deliver landscape A4 Word document.

This skill produces a **standalone Python script** that imports `report_renderer` and
calls `render(CFG, SECTIONS)`. When executed, it writes a `.docx` file to the path
resolved by `resolve_output_path(CFG)`.

After writing the script, execute it immediately with `python <script_path>` and confirm
the saved path printed to stdout.

---

## Where the script lives

Every generated script is saved to:

```
clients/<domain>/<date_slug>/work/<report_name>_<date_slug>.py
```

Example:
```
clients/example.com/2026-06/work/hreflang_diagnose_2026-06.py
```

The script is an audit artifact — it belongs to the specific audit, not to the project root.

**Never write report scripts to the project root.**

The infrastructure lives in the same directory as this skill:
```
.claude/skills/seo-report-generator/
  docx_helpers.py      ← stable — colors, helpers, setup_document()
  report_config.py     ← stable — output path resolution
  report_renderer.py   ← stable — generic renderer
```

## Mandatory Pre-Script Evidence Registration (blocking gate)

**This step must be completed before writing a single line of SECTIONS.**

Do not skip this step. Do not defer it to the pre-save checklist.

### Procedure

1. **Read `clients/evidence_registry.md`** — establish the current highest E-NNN.

2. **Enumerate every observation** that will become an Evidenz cell in the script.
   Go through every planned table row, one by one.
   Write out the list in plain text: observation → intended evidence reference.

3. **For each observation, ask: does a registered E-NNN exist whose description
   accurately and specifically covers this observation?**
   A match requires that the registered description names the same fact, metric, and URL
   count as the cell. "Close enough" or "related topic" is not a match.

4. **If no accurate match exists: register the new entry in `clients/evidence_registry.md`
   immediately** — before writing the script. Assign the next available ID.

5. **Only after all observations have a registered, accurate E-NNN** — write the script.

### What counts as a mismatch (do not recycle these)

- The registered description names a different metric (e.g., keyword presence vs. customer claim)
- The registered description names a different URL count or scope
- The registered description covers a related but distinct observation
- The only reason to use an ID is that it was the most recently assigned one

### Why this is a blocking gate, not a checklist item

Checklist items are verified after writing. This step must happen before writing,
because a wrong ID written into SECTIONS propagates into the registry update, the
evidence ledger, and the final .docx — all of which are hard to audit retroactively.

## Non-Negotiable Script Structure

Every generated script has exactly this structure — nothing else:

```python
# ══════════════════════════════════════════════════════════════════════════════
# SECTION 1 — CFG + SECTIONS
# Generated by Claude after analysis and confirmed with the user.
# All values are derived from the current audit's source files.
# No value may be invented, assumed from prior knowledge, or carried over
# from a previous audit without re-verification against the current data.
# ══════════════════════════════════════════════════════════════════════════════

CFG = {
    "domain":        "<domain>",
    "report_title":  "<ReportTitle>",
    "report_name":   "<report_name_stem>",
    "date_label":    "<MonthYear>",
    "date_slug":     "<YYYY-MM>",
    "data_sources":  "<source description>",
    "subtitle":      "<subtitle line for page 1>",
    "baseline":      0,      # indexable HTML URL count — from file_inventory
    "output_dir":    None,   # None = auto-resolve; only set if user specifies a path
}

SECTIONS = [
    # Populated by Claude from analysis results confirmed with the user.
    # Structure and column definitions are derived from the analysis,
    # not from fixed templates.
]

# ══════════════════════════════════════════════════════════════════════════════
# SECTION 2 — RENDER CALL (always identical)
# ══════════════════════════════════════════════════════════════════════════════

from report_renderer import render
render(CFG, SECTIONS)
```

## How to populate SECTIONS

### Block types

All supported block types. Use only these — the renderer raises an error on unknown types.

**Heading:**
```python
{"type": "heading", "text": "1.  Datenbasis", "level": 1}
{"type": "heading", "text": "2a.  Sub-section", "level": 2}
```
- `level=1`: always page break before, NAVY 13pt
- `level=2`: no page break, DBLUE 11pt

**Body text:**
```python
{"type": "bt", "text": "Freitext-Kommentar zum vorangegangenen Cluster..."}
```

**Note / caption:**
```python
{"type": "note", "text": "Basis: Screaming Frog Crawl Juni 2026. Scope: indexierbare HTML-URLs."}
```

**Spacer:**
```python
{"type": "spacer"}
```

**Table:**
```python
{
    "type":    "table",
    "columns": ["Col A", "Col B", "Col C", "Evidenz"],
    "widths":  [6.0, 8.0, 7.6, 4.5],
    "rows": [
        {"bg": "LRED",   "cells": ["val1", "val2", "val3", "E001 | file.csv | field"]},
        {"bg": "LYELL",  "cells": ["val4", "val5", "val6", "E002 | file.csv | field"]},
        {"bg": "LGREEN", "cells": ["val7", "val8", "val9", "E003 | file.csv | field"]},
    ],
    "summary": {"bg": "NAVY", "cells": ["Gesamt", "...", "...", "E001-E003 | file.csv"]},
}
```

## Rules for CFG

- `baseline` must come from the current audit's `file_inventory` (indexable HTML URL count).
  If not yet available: stop, do not default to any number, ask the user.
- `output_dir`: leave as `None` unless the user explicitly provides a path.
- No hardcoded absolute paths anywhere in the script.

## Rules for SECTIONS

### Derivation rule

Column definitions, section order, cluster groupings and table structure are all
**derived from the analysis**, not from fixed templates.

After clustering and analysis, Claude decides:
- which sections the report needs
- what columns each table requires
- how many rows each table has

This means: two reports on the same topic may have different table structures
if the data warrants it.

### Value formatting rule

**All cell values must be pre-formatted strings before being written into `cells`.**

The renderer does no calculations. Every value that requires formatting must be
pre-computed by the script before writing it into `cells`.

You may use `pct()` from `docx_helpers` to format percentage values — call it
in the script body before assigning to `cells`, not inside the list literal:

```python
from docx_helpers import pct

# Correct — pre-formatted before assignment
count = 1180
baseline = 4866
"cells": [pct(count, baseline), "Hoch", "E001 | internal.csv | count"]
# → "1180 (24,2 % von 4866 URLs)"

# Also correct — inline f-string
"cells": [f"{count} ({count/baseline*100:.1f} % von {baseline} URLs)", "Hoch", "E001 | internal.csv | count"]
```

This applies to all computed values:
- percentage calculations via `pct(n, baseline)` or inline f-string
- date formatting
- number formatting with thousands separators
- any derived labels

### Handlungsempfehlung placement rule

**Single-issue tables** (one issue per table, e.g. one sub-section heading covers exactly one issue ID):
- Do **not** add a "Handlungsempfehlung" column to the table.
- Place the recommendation as a `{"type": "bt", ...}` block directly below the table.

**Multi-issue tables** (two or more distinct issue IDs in the same table):
- Add a **"Handlungsempfehlung"** column as the second-to-last column, immediately before "Evidenz".
- Each row gets its own concise recommendation (1–2 sentences max).
- Width allocation: give "Handlungsempfehlung" at least **6.5 cm** and at most **9.0 cm**.
  Compensate by narrowing other columns (e.g. short label columns, numeric columns) so the
  total stays ≈ 26.1 cm. If the table cannot fit with a minimum 6.5 cm recommendation column,
  split it into two single-issue tables instead and apply the single-issue rule.

Column order for multi-issue tables:
```
[content columns...] | Handlungsempfehlung | Evidenz
```

### Evidence rule

Every table must have a final column named **"Evidenz"**.

Format for every evidence cell:
```
"<issue_id> | <source_file> | <field or calculation>"
```

Examples:
- `"ITR001 | internal_redirection_(3xx)_inlinks.csv | count(Destination URL)"`
- `"IBL004 | pyroweb.de-link-intersect.csv | DR >= 30, intersect=0"`
- `"IHL001 | hreflang.csv | missing return link, rows 14-47"`

Never leave the Evidenz cell blank or use a generic string without an issue_id.

### Background color rule

Use these named values for `bg`:

| Value    | Meaning                          |
|----------|----------------------------------|
| `LRED`   | Kritisch                         |
| `LYELL`  | Hoch                             |
| `LGREEN` | Mittel / OK / Positiv            |
| `LGREY`  | Niedrig / alternating neutral    |
| `WHITE`  | Default row background           |
| `NAVY`   | Summary / total rows             |

Or any 6-char hex string for custom backgrounds.

## Document structure rules

### Default section order

The default structure is:

| # | Heading | Content |
|---|---------|---------|
| Title block | — | Handled by `setup_document(CFG)` — no block needed |
| 1 | Datenbasis | Source table: Quelle \| Stand \| Scope \| Limitierung (+ any relevant columns) |
| 2 | Zusammenfassung der Kernergebnisse | Color-coded summary of all clusters/issues |
| 3 | Gesamturteil | Verdict table + bt() paragraph |
| 4+ | \<Issue cluster sections\> | One or more sections, structure derived from analysis |
| Last | Handlungsempfehlungen | Prioritized action plan |

**This structure is the default, not a fixed template.** Additional sections may be added
or existing sections omitted when the analysis warrants it — decided per chat and per
audit scope. The title block is always present. Section order is determined by the analysis.

All section headings use `"level": 1` (page break before).
Sub-sections within a section use `"level": 2` (no page break).

### Column width constraint

Total usable width = 29.7 − 1.8 − 1.8 = **26.1 cm**

The sum of `widths` in every table must be ≈ 26.1 cm.

```
Narrow:  0.5–1.5 cm   (numbering, short codes)
Short:   2.0–3.0 cm   (labels, severity)
Medium:  4.0–6.0 cm   (names, categories)
Long:    7.0–11.0 cm  (descriptions, findings)
Evidenz: 4.0–6.0 cm   (always last column)
```

## Summary Reports ("ToDo-Zusammenfassung" / "High-Priority Cross-Report")

### Purpose

A summary report aggregates high-priority findings across all topic reports of a single
audit into one consolidated action list. It does not re-render the individual reports —
it adds a new synthesis layer on top of them.

### Data source: gen_*.py scripts, NOT the .docx files

Do **not** read the generated `.docx` files to extract findings. Reading tables from Word
documents via `python-docx` is fragile and order-dependent.

Instead, read all `gen_<topic>_<date_slug>.py` scripts in `clients/<domain>/<date_slug>/work/`.
These scripts contain the authoritative structured data behind every report:
- `CFG["report_title"]` → topic label
- `SECTIONS` rows with `"bg": "LRED"` or `"bg": "LYELL"` → Kritisch / Hoch priority
- `cells` values → issue text, affected URL count, recommendation
- Last `cells` element (Evidenz column) → source evidence

### Extraction procedure

1. Glob all `gen_*.py` files in `work/` — exclude `gen_summary_*.py` to avoid recursion.
2. For each script, parse `SECTIONS` in Python (import or `ast.literal_eval` the data structure).
3. Collect all table rows where `bg in ("LRED", "LYELL")`.
4. For each collected row, record:
   - `topic` from `CFG["report_title"]`
   - `issue_id` from the Evidenz cell (first token before ` | `)
   - `issue_text` from the first cell
   - `affected` from the cell that contains a number or percentage (typically cell 2 or 3)
   - `priority` from the cell containing "Kritisch" / "Hoch" / or derived from `bg`
   - `recommendation` from the corresponding Handlungsempfehlungen table row (matched by issue_id or topic)
   - `evidenz` from the last cell

5. Group by topic. Sort: Kritisch first, then Hoch. Within each group, preserve original row order.

### Practical note on parsing

The `gen_*.py` scripts are valid Python modules. The safest extraction approach is to
`exec()` the script body in a controlled namespace and read `CFG` and `SECTIONS` directly:

```python
import ast, pathlib

ns = {}
exec(pathlib.Path("gen_pagespeed_2026-06.py").read_text(encoding="utf-8"), ns)
cfg = ns["CFG"]
sections = ns["SECTIONS"]

high_rows = [
    (cfg["report_title"], row)
    for block in sections
    if block.get("type") == "table"
    for row in block.get("rows", [])
    if row.get("bg") in ("LRED", "LYELL")
]
```
